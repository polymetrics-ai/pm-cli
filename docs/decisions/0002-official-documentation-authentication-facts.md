# 0002: Official documentation facts admitted for GitHub REST authentication and pagination

Date: 2026-09-19. Status: approved architectural adjustment, recorded. The capture that this decision refers to exists (`connectors/github/official-documentation/`); the compiler-side source admission and normalization mechanism does **not** exist yet, and nothing in this record admits a fact at runtime. This decision covers one declared operation only and does not authorize application work.

## Decision

The pinned OpenAPI capture for the `github` connector declares no security scheme (`security`/`securitySchemes` absent) and no cursor parameter, so the compiled operation for `issues/list-for-repo` is unauthenticated *by declaration* and paginates by page number only. **Missing OpenAPI metadata is not evidence of anonymous-only operation.** Immutable official provider documentation may therefore supply typed authentication, pagination and returned-URL facts that OpenAPI does not declare, through an explicit source admission and normalization mechanism, provided that provider protocol facts stay separate from connection policy.

## Exact facts admitted

Each fact below is admitted only together with the verbatim quotes and locators recorded for it in the manifest (facts `F1`–`F4`). The quotes given here are the manifest's verified quotes, shortened only where marked.

**F1 — `rest_bearer_authorization_header` (provider protocol fact).** GitHub's REST API documents that a token is presented in the `Authorization` request header, in the form `Authorization: Bearer <TOKEN>` or `Authorization: token <TOKEN>`; a JSON web token must use the Bearer form. Verbatim, from `authenticating-to-the-rest-api.html` anchor `#about-authentication`: "After creating a token, you can authenticate your request by sending the token in the Authorization header of your request." and "In most cases, you can use Authorization: Bearer or Authorization: token to pass a token. However, if you are passing a JSON web token (JWT), you must use Authorization: Bearer." GitHub's own code sample on the operation's page sends the Bearer form: `curl -L \ -H "Accept: application/vnd.github+json" \ -H "Authorization: Bearer <YOUR-TOKEN>" \ -H "X-GitHub-Api-Version: 2026-03-10" \ https://api.github.com/repos/OWNER/REPO/issues` (anchor `#list-repository-issues--code-samples`).

**F2 — `rest_link_header_pagination` (provider protocol fact).** A paginated REST response carries a `link` response header, omitted when the endpoint does not paginate or everything fits on one page, whose URLs address the previous, next, first and last page and are annotated `rel="prev"`, `rel="next"`, `rel="last"`, `rel="first"`; the URLs use query parameters, whose families may differ between endpoints, and "each paginated endpoint will use the page, before/after, or since query parameters" (anchor `#using-link-headers`). The article's own example request in that same section lists issues on `https://api.github.com/repos/octocat/Spoon-Knife/issues`, and the sentence "If the response is paginated, the link header will look something like this:" presents the example `link` header as the continuation such a response would carry; the pairing is therefore shown by two adjacent examples and the sentence between them in one section, and the article never states that the two routes address the same resource. The published example value is: `link: <https://api.github.com/repositories/1300192/issues?page=2>; rel="prev", <https://api.github.com/repositories/1300192/issues?page=4>; rel="next", <https://api.github.com/repositories/1300192/issues?page=515>; rel="last", <https://api.github.com/repositories/1300192/issues?page=1>; rel="first"`, while the example request published in the same section uses `https://api.github.com/repos/octocat/Spoon-Knife/issues`. Page numbering is also documented: `per_page` controls results per page where supported and "For most endpoints, the maximum value of per_page is 100", silently reduced rather than refused (anchor `#changing-the-number-of-items-per-page`).

**F3 — `get_repos_owner_repo_issues_documented_semantics` (provider operation documentation).** The published documentation for `GET /repos/{owner}/{repo}/issues` states its summary ("List issues in a repository. Only open issues will be listed."), its pull-request caveat, its four custom media types, that the endpoint works with fine-grained tokens holding `"Issues" repository permissions (read)` *and* that "This endpoint can be used without authentication or the aforementioned permissions if only public resources are requested." (anchor `#list-repository-issues--fine-grained-access-tokens`), its complete parameter set as published (one `accept` header; path parameters `owner` and `repo`; query parameters `milestone`, `state` (default `open`; `open`/`closed`/`all`), `assignee`, `type`, `creator`, `mentioned`, `issue_field_values`, `labels`, `sort` (default `created`; `created`/`updated`/`comments`), `direction` (default `desc`; `asc`/`desc`), `since`, `per_page` (default 30, max 100), `page` (default 1)), and its response status codes 200 OK, 301 Moved permanently, 404 Resource not found, 422 Validation failed, or the endpoint has been spammed. The operation page publishes **no** response-header table, so the `link` header is not documented on that page; it comes from F2 and from the pinned OpenAPI declaration.

**F4 — `rest_best_practices_use_returned_urls_and_link_headers` (provider protocol fact).** GitHub's REST API best-practices article instructs clients not to parse URL values or predict URL structure (`best-practices-for-using-the-rest-api.html`, anchor `#do-not-manually-parse-urls`: "You should not try to parse these URLs or to predict the structure of future URLs. This can cause your integration to break if GitHub changes the structure of the URL in the future."), and not to construct pagination queries: "Similarly, you should not try to manually construct pagination queries. Instead, you should use the link headers to determine what pages of results you can request. For more information, see Using pagination in the REST API." Its only instruction to follow a URL that a response returns concerns HTTP redirection, not pagination: "Receiving an HTTP redirection is not an error, and you should follow the redirect." (anchor `#follow-redirects`). The article names no pagination parameter and no next-page URL; the places it does not reach are recorded as absences A4, A5 and A7 in the manifest (A6 records the equivalent check for the pagination article's two example routes).

Documented absences and unverified items are recorded as machine-readable records in the manifest. Everything the retained bytes state but that this decision does **not** admit is listed there, including: the retained pagination article pairs an example request on `/repos/octocat/Spoon-Knife/issues` with an example `link` header on `/repositories/1300192/issues` (two adjacent examples in one section, joined by the pairing sentence), but no retained document states that the two routes address the same resource, so the route pairing is admitted as shown by example only; no retained document states that this operation accepts an `after` cursor; no retained document defines PM's navigation policy, which is a PM rule recorded elsewhere and neither established nor relaxed by these documents; no retained document states that GitHub requires a token for every public read, or that this connection may call the provider without one; no page revision or last-updated identity is exposed by the retained pages (no ETag, no Last-Modified); the license position is stated for the `github/docs` repository and only inferred for the rendered page bytes.

## Precedence and conflict rules

1. **OpenAPI is authoritative for what it declares.** Paths, parameters, media types, response statuses, declared response headers, and declared security/`securitySchemes` in the pinned source set are never overridden by a supplemental documentation fact.
2. **Supplemental facts may only add what OpenAPI does not declare** — here: no declared authorization channel on the operation, and no declared cursor parameter. A fact is admissible only against a genuine declaration gap.
3. **A supplemental fact may never contradict OpenAPI.** A contradiction is refused as a source conflict; it is never reconciled by preference, and the frozen OpenAPI bytes are never reinterpreted or edited to fit the documentation.
4. **A supplemental fact may never widen origins, credentials or capabilities.** It may not add or enlarge a credential channel beyond what the declared operation carries, may not add operations, parameters, media types, statuses or response headers beyond the declared operation, and may not re-identify the resource address or the declared origin (`https://api.github.com`). In particular, F1 states that a bearer mechanism *exists*; it does not make the compiled operation authenticated. That requires the operation's compiled bundle to declare `execution.http.authorization` through the connector's own declared source, which is a separate change owned elsewhere.
5. **Provider protocol facts stay separate from connection policy.** F1 is a protocol fact. The requirement that *this* private connection present a server-held credential is a PM connection declaration; it is neither established nor weakened by these documents, and the two must never be conflated in a compiled bundle, a receipt or a diagnostic.
6. **An observation is not an authority.** The published `link` value is an example of what a provider may send. It does not authorize replaying a provider-supplied URL and does not relax PM's navigation rule that a continuation must stay on the declared operation identity (same origin, same escaped path, unchanged unrelated query parameters).
7. **Scope: this operation only.** The admitted facts cover `issues/list-for-repo` (`GET /repos/{owner}/{repo}/issues`) and nothing else. The pagination article is written about the REST API generally; its generic statements may not be projected onto another endpoint by this decision, and each further operation needs its own admission.

## What this decision does not do

- It does not modify, replace or reinterpret the pinned OpenAPI capture, its lock file or its semantics document, and it declares no generated output identity.
- It does not make any operation authenticated, does not add a credential channel to source, and does not change any navigation, pagination or refusal rule in the runtime.
- It does not admit the `after` cursor, does not treat the example pairing of `/repos/octocat/Spoon-Knife/issues` with a `/repositories/1300192/issues` continuation as a statement of route identity, and does not admit any claim that a token is mandatory for public reads.
- It does not change PM's navigation policy: the recorded route pairing and the best-practices guidance are provider protocol facts, and PM's rule that a continuation must stay on the declared operation identity is unchanged and recorded elsewhere.
- It does not generalize to other GitHub endpoints or to other connectors; the mechanism may later be reused, but each source admission is its own decision.
