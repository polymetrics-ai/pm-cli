# Shared engineering and review policy

Accepted application engineering policy; this policy does not itself grant implementation, publication, CI, or merge authority. [IMPORT-MANIFEST](../IMPORT-MANIFEST.json) owns candidate state, granted import/publication authority, and remaining verification/merge conditions. Accepted product and content decisions remain settled; acceptance alone does not establish passing checks, implementation readiness, or an approved landed baseline.

PM has one remote-first Go/Gin/PostgreSQL/Temporal/shared-artifact architecture. The CLI and browser call the same versioned API. Server application services own authorization and durable state; worker activities own provider I/O and credential resolution. Domain code accepts context.Context and typed contracts; framework contexts stay in adapters. Source descriptors and the Foundation Atlas cannot establish executable reachability or provider proof. The five initial connectors and seven lane inventories do not imply complete provider parity.

Read the accepted issue and its explicitly linked versioned contracts. Preserve first-owned files and later integration/update rights. Dependencies order implementation within a coherent candidate; they do not require issue-by-issue review or automatic per-issue merges. Where CodeGraph is present, use it first to locate code; otherwise use normal source tools. Use the project pm-go router and relevant installed references only. No task may silently install tools, add libraries or change accepted architecture.

For changed behavior, create and execute the focused causal failing check before production edits, implement the scoped change, and run the affected checks before integration. Create tests this issue owns rather than treating their absence as a prerequisite failure. Missing merged prerequisite tests are discrepancies. Use focused standard Go tests and table subtests by default. Add integration, concurrency, security, recovery and regression checks where the accepted validation map requires them. Compilation, whitespace checks, missing or zero tests, unexpected skips, or mocks labeled live cannot satisfy behavioral acceptance. Documentation uses content, link and instruction-discovery checks rather than invented runtime RED. All planned PM checks in this preparation are UNEXECUTED.

Verify the authorized implementation and independent reviewer environments before relying on their results. Implementation and independent review are distinct roles; an implementer cannot supply its own independent review. Record the actual assigned role, route/model metadata, and authentication evidence without credentials. Application engineering instructions are model-neutral: operational routing comes from one operator-owned source and must not be copied into this policy. Do not use a fallback or prewalk route; a route mismatch stops the affected work without authorizing global configuration or shared-tool changes.

OMP is PMCLI's sole project coordinator and integration owner. Keep one writing owner for each integration branch; independent reviewers are read-only. Firstmate and no-mistakes initialization, custody, fixing, promotion, push, and CI ownership are not PMCLI workflow requirements. Preparation does not install, restart, or change shared tooling, and does not qualify future implementation environments.

Use the pinned [AI Hero code-review reference](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/code-review/SKILL.md), MIT, once for each dependency-coherent completed PR candidate, not for each todo or issue. Run one independent read-only Standards reviewer and one independent read-only Spec reviewer in parallel. Standards receives PM application instructions and linked standards; Spec receives every included accepted issue, incorporated amendment/comment, and immutable context. Keep reports separate. Record the accepted comparison scope, target revision at intake, resolved merge-base and commit list, actual reviewed candidate head, route evidence, standards/spec digests, findings, and dispositions. Missing independent reviewers, an inaccessible spec, an empty applicable code diff, or an unapproved comparison base blocks that review. Reviewing issue specifications remains a separate read-only activity, not a code-diff review.

The delivery sequence is: focused causal checks, scoped implementation and focused checks, integration of the coherent completed candidate, one Standards/Spec pair, material fixes, affected checks and targeted review of the changed diff, genuine required CI on the actual final candidate, then separately authorized merge. A materially changed head must receive the targeted review its change affects; do not repeat unchanged full reviews. Heuristic smells are not hard gates, but concrete defects remain blocking until fixed. Missing, skipped, stale, or different-head CI is not green.
