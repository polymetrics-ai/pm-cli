## Durable admission, identity and repair

**Proposed acceptance transaction:** authenticate actor/service identity and explicit workspace; validate plan/approval revision and immutable input references; enforce idempotency-key uniqueness plus request fingerprint; lock/reserve run, bytes, requests, concurrency and deadline budgets; insert immutable RunSpec, run, audit/event and `StartRun` outbox row; **commit before202** with run URL. Same key/different fingerprint is409; response loss retried with same key returns the accepted run. A failed commit never produces202. Temporal outage can leave bounded accepted work queued while PG remains healthy; backlog-age/capacity admission limits reject new work when exceeded. PG outage refuses new durable admission.

**Observed APIs:** `client.ExecuteWorkflow`, `StartWorkflowOptions.ID/TaskQueue/WorkflowIDConflictPolicy/WorkflowIDReusePolicy/WorkflowExecutionErrorWhenAlreadyStarted`; `DescribeWorkflowExecution`, `GetWorkflow`, `GetWorkflowHistory`, `CancelWorkflow`. SDK reuse defaults allow duplicates and duplicate-start errors are suppressed unless explicitly requested; configure policies. [internal/client.go:1154–1222](https://github.com/temporalio/sdk-go/blob/b7c242c6894df088a57a85b33d0586e908da8b93/internal/client.go#L1154-L1222) [internal/client.go:433–454](https://github.com/temporalio/sdk-go/blob/b7c242c6894df088a57a85b33d0586e908da8b93/internal/client.go#L433-L454) [docs/encyclopedia/workflow/workflow-execution/workflowid-runid.mdx:79–147](https://github.com/temporalio/documentation/blob/bc5c548f28d0bc0b72e31976e2865563f40a85fc/docs/encyclopedia/workflow/workflow-execution/workflowid-runid.mdx#L79-L147)

**Proposed identity:** namespace `pm-prod` per environment/trust deployment, not per user; workflow ID `pm/run/<opaque PM run UUID>`; PM run UUID never changes. Temporal RunID changes across ContinueAsNew; persist first/current observed execution IDs only as bindings. User-visible effects are keyed by PM intent/member IDs, never Temporal attempt or RunID. Start with conflict `WORKFLOW_ID_CONFLICT_POLICY_FAIL`, reuse `WORKFLOW_ID_REUSE_POLICY_REJECT_DUPLICATE`, error-when-already-started=true. The outbox treats AlreadyStarted as a reconciliation branch and checks the bound RunSpec/version/namespace; it never terminates or silently adopts an unrelated existing workflow.

| Failure window / observation | Proposed repair |
|---|---|
| PG commit, process death before Temporal start | another dispatcher claims bounded outbox work and starts the same workflow ID |
| Temporal accepts, RPC response or outbox acknowledgement lost | retry same identity; AlreadyStarted -> Describe/history binding -> mark delivered; no second logical run |
| Workflow open, completion projection activity failed | retry an idempotent `FinalizeRunProjection` activity with its own bounded policy; workflow replay repeats coordination without repeating settled effects |
| Workflow closed and history retained, final PM projection missing | reconciler reads exact execution/history closure, idempotently repairs orchestration projection; effect success still requires PM receipts/checkpoints. A closed workflow cannot execute a missing final activity merely because code was changed |
| Temporal says NotFound, PG proves never bound and no dispatch | retry stable start under PG claim/fence; every first activity validates immutable run binding and current execution generation before provider work |
| Temporal says NotFound after prior binding, retention expiry, restore or uncertain start | absence does not prove never executed. Mark `orchestration_unknown`; inspect PM effect/member receipts and immutable artifacts. Safe read/recovery may be re-driven under a new audited orchestration generation; ambiguous writes remain blocked for exact reconciliation |
| Closed failed/canceled/terminated execution | preserve closed state; an authorized resume creates an explicit recovery generation, checks current budgets/authorization and reuses unresolved PM intent IDs; never automatic whole-run retry or reset |
| PM terminal, Temporal open or a late duplicate starts after retention | terminal/generation guard makes subsequent activities no-op or safe fail; reconcile/cancel stale coordination; never overwrite terminal effect facts |

**Observed limit:** reject-duplicate applies only to retained closed executions; IDs are plaintext and outside payload codecs. Therefore PG idempotency/effect records outlive Temporal history and IDs contain only opaque safe values. Configure explicit retention (proposed30days), but do not present it as permanent deduplication. Never decide absence through visibility lists. No two-system atomic-commit claim. ## Workflows, effects and limits

**Observed:** deterministic workflow code uses `workflow.Now/Sleep/Go/Channel/Selector`, stable iteration and `workflow.ExecuteActivity`; I/O belongs in activities. [workflow/doc.go:71–114](https://github.com/temporalio/sdk-go/blob/b7c242c6894df088a57a85b33d0586e908da8b93/workflow/doc.go#L71-L114)

**Proposed:** workflows carry only RunRef, immutable version IDs, bounded counts/reasons and safe checkpoint references. Activities fetch authorized PG rows, resolve server-owned credentials immediately before I/O, access providers/storage, publish manifests and settle member effects. Bounded synchronous metadata/read endpoints may stay synchronous with the same authorization/limits. No raw secret, bulk row, sensitive query text, provider response body or bearer URL in workflow arguments/results, heartbeat details, search attributes, error messages or logs. Data converters are defense in depth; they do not hide identifiers/search metadata. Errors carry registered safe codes and incident IDs.

**Proposed durable-effect sequence:** PG intent/member identity -> physical dispatch attempt record and budget charge -> external request -> exact per-member receipt/readback -> checkpoint/event commit. Replay/retry consults the ledger first. If remote acceptance occurs without local acknowledgement, mark unknown; retry only with the same proven provider idempotency key or authoritative exact-ID/field readback. Counts are insufficient. A PG generation fence prevents stale local commits, not a provider effect already sent. ETL publishes immutable verified object bytes first, then atomically commits PM manifest+cursor; orphan object GC is delayed and reference-aware. No cross-object-store/PG transaction or shared writable DuckDB file.

**Observed timeout/retry APIs:** `workflow.ActivityOptions.ScheduleToCloseTimeout` bounds all attempts, `StartToCloseTimeout` bounds an attempt, `HeartbeatTimeout` plus `activity.RecordHeartbeat` detects loss and delivers cancellation; `WaitForCancellation` defaults false. Default activity retries can be unlimited; explicit policies are necessary. [internal/activity.go:100–161](https://github.com/temporalio/sdk-go/blob/b7c242c6894df088a57a85b33d0586e908da8b93/internal/activity.go#L100-L161) [internal/activity.go:274–294](https://github.com/temporalio/sdk-go/blob/b7c242c6894df088a57a85b33d0586e908da8b93/internal/activity.go#L274-L294)

**Proposed retry ownership:** Temporal owns retry timing for a safe logical activity; the provider transport makes one physical request per recorded attempt. Disable independent application HTTP retry loops. The shared adapter classifies definitely-unsent, safe retryable read/idempotent write, permanent rejection and unknown effect. Unknown effects transition to reconciliation, not automatic blind resend. Retry-After becomes a shared account cooldown plus durable workflow delay. All retries consume immutable run budgets. Transport deadline < activity attempt timeout; long activities heartbeat safe cursor IDs and check cancellation before each bounded batch. Workflow execution deadline survives ContinueAsNew; do not accidentally reset the user's run budget. Cancellation stops future admission/dispatch, requests activity shutdown and settles in-flight ambiguity; forced termination cannot run cleanup and cannot assert external rollback.

**Observed defaults:** per-event blob error2MiB/warn512KiB; history error50MiB/51,200events, warn10MiB/10,240events; server suggests ContinueAsNew at4MiB. Each incomplete-operation category has a2,000 default. **Proposed PM caps:** encoded workflow/command payload64KiB, error summary1KiB, fanout at most32 in-flight bounded batch activities/run; ContinueAsNew at server suggestion OR2,000events OR2MiB, well before hard limits. Persist cursors/member progress in PG; roll over only at safe batch boundaries. Check `workflow.GetInfo(ctx).GetContinueAsNewSuggested/GetCurrentHistoryLength/GetCurrentHistorySize`; drain buffered signals and await `workflow.AllHandlersFinished` before `workflow.NewContinueAsNewError`. Application tests must prove signals/updates crossing rollover are retained. ## Replicas, tenancy and worker upgrades

**Observed:** `WorkerActivitiesPerSecond` is per worker; `TaskQueueActivitiesPerSecond` is server-wide for one queue. `Priority.FairnessKey/FairnessWeight` are available, but server1.31.2 `matching.enableFairness` defaults false. These mechanisms are not shared provider-account request limits. [internal/worker.go:149–196](https://github.com/temporalio/sdk-go/blob/b7c242c6894df088a57a85b33d0586e908da8b93/internal/worker.go#L149-L196) [internal/client.go:1413–1433](https://github.com/temporalio/sdk-go/blob/b7c242c6894df088a57a85b33d0586e908da8b93/internal/client.go#L1413-L1433) [common/dynamicconfig/constants.go:1419–1433](https://github.com/temporalio/temporal/blob/19a774302c613da9adc4436ab14278ccdca8e0a5/common/dynamicconfig/constants.go#L1419-L1433)

**Proposed:** a small fixed task-queue set by workload/isolation class (control, read/ETL, effect/write, binary/query) with explicit workflow/activity slots, queue rates and one deployment namespace. Configure matching fairness explicitly and use opaque tenant fairness keys plus bounded work units; test no starvation across replicas. PG admission reserves per-tenant slots; transactional PG provider-account permits/cooldowns are keyed by canonical provider account/auth cohort, across connection aliases and queues. Every physical request consumes a permit; unknown requests are charged, not refunded. Avoid waiting for permits while occupying activity slots: return a safe next-eligible time and let Temporal schedule a timer. This permit store is resource admission, not an execution/schedule engine.

A permit lease/fence cannot cancel a remote effect or guarantee provider-observed timing under arbitrary process pauses. Recheck grant expiry at dispatch, bound network lifetime, conservatively retain unknown in-flight capacity and honor provider responses; scope the tested guarantee to PM dispatch admission. Any throughput/fairness claim requires multi-replica tests including stale workers, clock skew, shared account aliases and PG outage.

**Observed RLS:** enable+policy defaults deny; owners normally bypass, superuser/BYPASSRLS always bypass; FORCE can constrain owners. RLS excludes TRUNCATE and referential checks, and cross-table policy reads have race caveats. SET LOCAL ends at transaction completion; `set_config(name,value,true)` provides parameterized transaction-local configuration. [doc/src/sgml/ddl.sgml:2376–2434](https://github.com/postgres/postgres/blob/7d3e000c5961a544302072058a1184e9a588837b/doc/src/sgml/ddl.sgml#L2376-L2434) [doc/src/sgml/ddl.sgml:2688–2717](https://github.com/postgres/postgres/blob/7d3e000c5961a544302072058a1184e9a588837b/doc/src/sgml/ddl.sgml#L2688-L2717) [doc/src/sgml/ref/set.sgml:46–66](https://github.com/postgres/postgres/blob/7d3e000c5961a544302072058a1184e9a588837b/doc/src/sgml/ref/set.sgml#L46-L66) [doc/src/sgml/func.sgml:26267–26282](https://github.com/postgres/postgres/blob/7d3e000c5961a544302072058a1184e9a588837b/doc/src/sgml/func.sgml#L26267-L26282)

**Proposed security:** application authorization **plus** tenant/workspace RLS on PM scoped tables. Every repository transaction begins with verified tenant/workspace/actor scope using parameterized `set_config(...,true)`, and every policy has USING plus WITH CHECK; missing/empty scope denies. Scope composite foreign/unique keys to tenant/workspace and map constraint errors without cross-tenant disclosure. API/worker runtime roles are non-owner, NOSUPERUSER/NOBYPASSRLS, without DDL/TRUNCATE/role grants; migrations use isolated identities. All exits commit/rollback before returning a pooled connection; destroy a connection if cleanup fails, and reject inherited session scope. No session SET, global-current-workspace, or raw customer SQL on the PM pool.

Worker service authentication is separate from attributed human/agent authorization. A private authenticated Temporal connection/mTLS plus authorizer and limited namespace/task access identifies the worker; it loads a persisted run grant and checks current membership/revocation, connection scope and generation before sensitive effects. A payload's tenant ID is not authority. Cross-tenant dispatch scanning, if necessary, is a narrowly owned control operation returning only claim refs; worker activities re-enter scoped transactions. Tenant custom GUCs are defense against missing filters, not protection against a fully compromised trusted DB principal that can choose arbitrary scope. Do not advertise a task queue or shared Temporal namespace as a tenant security boundary. Keep Temporal/UI/admin tools private. [docs/production-deployment/self-hosted-guide/deployment.mdx:22–27](https://github.com/temporalio/documentation/blob/bc5c548f28d0bc0b72e31976e2865563f40a85fc/docs/production-deployment/self-hosted-guide/deployment.mdx#L22-L27)

**Proposed upgrade policy:** enable `worker.Options.DeploymentOptions` with `UseVersioning:true`, immutable `WorkerDeploymentVersion{DeploymentName,BuildID}`, pinned workflow behavior. Retain old workers for their open runs; use explicit tested ContinueAsNew upgrades and `workflow.GetVersion` for replay-compatible command changes. ## Operational cost, restore and falsifiers

**Proposed deployment:** explicit operator launcher starts PG, schema jobs, Temporal server, PM API/workers and shared object storage; remote CLI has no dependency processes. **Observed upgrade constraints:** Temporal upgrades progress one minor at a time, patch current minor first, and apply required schema changes before server rollout. Consecutive-version compatibility is not arbitrary downgrade compatibility. Performance failure changes capacity/partitioning, not to a hidden local product mode.

**Observed backup primitive:** PG base backup+continuous WAL permits point-in-time recovery; pg_dump is logical and cannot replace that WAL chain. [doc/src/sgml/backup.sgml:488–549](https://github.com/postgres/postgres/blob/7d3e000c5961a544302072058a1184e9a588837b/doc/src/sgml/backup.sgml#L488-L549)

**Proposed restore contract:** protect PM DB, both Temporal databases, immutable objects/manifests, encryption keys and server configuration/version provenance. A coordinated PG cluster backup can cover all three DBs at one DB point; it cannot transactionally include object storage or external providers. Separate-instance backups have an explicit consistency horizon. Proposed engineering targets RPO<=5min/RTO<=60min are UNMEASURED and require operator budget/restore drills. Temporal history retention/archival is not a substitute for backup or permanent PM effect identity.

After restore, fence old workers and disable outbound effects before replay/resuming schedules. Establish a restore epoch, compare PM receipts/artifact integrity with Temporal execution bindings, and quarantine the uncertain interval: restored state may omit a request that succeeded externally. PG and Temporal both restored consistently still do not erase real provider effects. Readbacks/idempotency retention may be insufficient; unresolved effects require operator disposition. Check keys are recoverable separately, rejected/unknown effects remain visible, object GC cannot delete restore-needed bytes, and no automatic orphan-workflow/start repair replays unknown writes. Loss of keys can make ciphertext irrecoverable; loss of WAL/object versions sets a real recovery floor. Keep volumes on upgrade failure; no implicit purge.
