## Selection and alternatives

**Proposed/Recommended.** Use one S3 API artifact contract across deployments, with **SeaweedFS4.46** as the bundled object service and operator-managed instances of the same service supported. A managed S3 service can qualify against the same contract; it must not be accepted merely because it advertises compatibility. Use **AWS SDK for Go v2 service/s3 v1.113.0** behind a small ArtifactStore interface. Keep immutable Parquet objects in this store, dataset membership/version/publication/checkpoint references in PM PostgreSQL, and **DuckDB1.5.5 / duckdb-go2.10505.0** as worker-private analytical execution. No shared writable DuckDB file, NFS warehouse, or filesystem artifact product path. Driver pins reuse473 research and remain subject to its native-platform smoke gate.

**Observed/Verified — official documentation.** DuckDB's in-process writable native database is owned by one process; its current documentation separately describes a beta remote protocol and PostgreSQL-backed DuckLake. No blanket claim that DuckDB can never support distributed data access is made. [Concurrency, lines507–529](https://duckdb.org/docs/current/connect/concurrency). **Inferred.** Independent query engines over immutable remote objects fit PM's required worker separation without sharing native database files.

## Object and publication contract

**Proposed/Recommended.** ArtifactStore exposes PutAttempt(stream, expectedSize, checksum), OpenRange(ArtifactRef), Stat, AbortMultipart and DeleteUnreferenced. The reference contains tenant/workspace, artifact ID, immutable random attempt key, SHA256, byte length, media type, optional schema snapshot ID and backend generation. It never contains provider secrets, server storage keys or a public arbitrary URL. Object existence alone does not make a dataset published.

1. PM allocates an attempt/object reservation in PostgreSQL with scoped owner and quota, then grants an authorized worker that exact write intent.
2. Worker uploads to a **unique attempt key**, records its own SHA256 and completes multipart. A timeout means upload outcome unknown; stat/range/full verification resolves it before publication. A retry that must write again uses a different attempt key. Never overwrite a published key or use S3 ETag as a universal content digest.
3. Worker checks size/digest and visibility through the configured adapter. PostgreSQL transaction verifies its fence, schema binding and preceding checkpoint version, commits object reference + new dataset manifest/version + page receipt + next checkpoint + outbox event atomically.
4. If upload succeeded but transaction failed, the object is unreferenced; a grace-period collector may delete it only after checking active reservations, accepted runs, manifests, proofs and retention/legal holds. If transaction committed but reply was lost, resume reads that manifest/checkpoint/receipt rather than fetching/committing again.
5. A reader loads one authorized manifest version in PostgreSQL and only its listed objects. It does not discover table membership by S3 LIST. Artifact digest or schema mismatch blocks affected work; it is never a warning followed by coercion.

**Observed/Verified — inspected source.** Seaweed PUT conditional checking resolves an existing object and evaluates ETag/header conditions ([s3api_object_handlers_put.go2245–2358](https://github.com/seaweedfs/seaweedfs/blob/d997fba1575583a89cf0cc50dc0150642286c86d/weed/s3api/s3api_object_handlers_put.go#L2245)). **Unknown.** This inspected helper alone does not establish linearizable conditional creation under concurrent gateways. **Proposed/Recommended.** PM does not rely on that unproven property for publication identity: unique immutable attempt keys and PostgreSQL fence/manifest admission own it. Still test conditional support used by SDK, multipart failure, two gateways, process loss, corruption and immediate cross-worker read.

**Proposed/Recommended.** Initially proxy client upload/download through the authorized PM API with bounded streaming, range/length/media validation and private IDs. Workers use infrastructure credentials scoped to artifact services; these are distinct from provider credentials and remain outside Temporal payloads. Ordinary clients cannot reach filer/master/volume endpoints. Uploads are data, never arbitrary paths/code/spec URLs. More efficient direct signed transfers can be added behind the same authorization and immutable artifact contract only after expiry/scope/leak tests.

## DuckDB execution and field fidelity

**Proposed/Recommended.** A warehouse task resolves authorized dataset manifests, materializes only admitted objects into its unique scratch directory, validates digests, mounts them read-only to a restricted analytical child process, registers approved relations, and executes a bounded query AST. Go binds scalar values; identifiers come from compiled schema IDs. Default query input is a typed relation/filter/project/aggregate expression, not arbitrary SQL text with table-function/file access. Customer PostgreSQL direct SQL is a separate connection-bound operation using its least-privilege provider identity and policy.

**Observed/Verified — official documentation.** DuckDB warns that hardening settings are defense in depth, not a full security boundary for untrusted SQL; external access can be disabled with explicit allowed paths, configuration locked, and memory/temp limits set. [Security, lines560–629 and652–669](https://duckdb.org/docs/current/operations_manual/securing_duckdb/overview). **Proposed/Recommended.** Disable network/external extension install/autoload, lock settings, run non-root, use process/container memory/CPU/time/disk bounds in addition to engine limits, pass no provider/storage credentials to the query process. Only controlled file paths are allowed for this task. Query process death fails/retries the read without endangering accepted connector effects. The exact child protocol/helper belongs in the file manifest; do not describe this as free sandboxing provided by DuckDB.

**Proposed/Recommended.** Preserve exact decimal/integer values with precision metadata and string/tagged API encodings where JavaScript numbers are insufficient. Preserve timestamp timezone/precision policy, arrays/unions and nullability from source facts. Parquet null is not an absent-field marker: retain per-field presence information when semantics require it, or reject that materialization before publication. Reverse ETL uses the immutable workset and mapping versions, not a fresh mutable warehouse query on retry. Tests cover null/absent/empty/default and out-of-range numbers through source → Parquet → query → destination payload.

## Bundled service topology and version locks

**Proposed/Recommended.** Use Docker Compose v5.5.1 as the default explicit one-host supervisor/launcher, Caddy v2.11.4 for TLS ingress, and paired PM API/worker OCI images built from one PM revision. The server stack contains PostgreSQL, Temporal server, PM API, PM worker, Seaweed master/volume/filer/S3, ingress; one-shot dependency-schema/bootstrap/PM-migration jobs complete before admission. A restricted analytical child runs under the worker supervisor. No full UI product is required now; a minimal browser parity harness is test tooling. Temporal UI is optional operator tooling, not the PM UI or a required public endpoint.

**Observed/Verified — registry manifest inspection, no execution.** IMAGE-PINS.json records current multiarchitecture index digests and per-platform digests for postgres16.15, temporalio/server1.31.2, temporalio/admin-tools1.31.2, chrislusf/seaweedfs4.46 and caddy2.11.4. All have Linux amd64/arm64 manifests. A manifest is not native smoke, image provenance attestation, CVE analysis or service readiness. Root source pins for Compose5.5.1 (5f94fb0aa42a2cd1248c6e6c7fafb87546b9c8de) and Caddy2.11.4 (e2eee6a7fce366321294c9c2a79f3146891dcbdf) are recorded. Both Apache2; Docker Desktop has separate distribution/use terms, so Linux Engine is the server baseline and macOS development uses an operator-installed compatible container runtime.

**Proposed/Recommended.** Final PostgreSQL baseline follows the Temporal specialist's source-qualified16.15 recommendation; the existence of newer PostgreSQL18.6 is not proof Temporal tests it. Small-stack one PG instance has separately owned databases/roles pm_app, temporal, temporal_visibility and pm_objects_meta. Separate instances are a resource/availability deployment choice using the same code and schemas. PM migrations never touch Temporal or filer tables; each product's migration/bootstrap tool owns its stores.

**Observed/Verified — inspected source.** The Seaweed default scaffold enables another filer backend and leaves postgres2 disabled, with sample SSL disabled and connection_max_open50. The actual postgres2 source warns that bounded connection pools can deadlock nested listing ([filer.toml145–181](https://github.com/seaweedfs/seaweedfs/blob/d997fba1575583a89cf0cc50dc0150642286c86d/weed/command/scaffold/filer.toml#L145), [postgres2_store.go36–65](https://github.com/seaweedfs/seaweedfs/blob/d997fba1575583a89cf0cc50dc0150642286c86d/weed/filer/postgres2/postgres2_store.go#L36)). **Proposed/Recommended.** Ship explicit PostgreSQL-only filer configuration with TLS, least-privilege metadata role and bounded gateway admission. Do not copy defaults or guess a safe connection_max_open value: qualify nested listing/pool saturation in M0, retain the result and configure that pool independently of PM pgx. Until qualified, object storage integration is planned, not production-ready. This is a concrete early dependency gate; a material failure requires replacing the object service across all deployments, not reverting to files.

**Observed/Verified — official documentation.** Compose distinguishes a started container from a healthy dependency and supports successful one-shot job dependencies. [Startup-order documentation](https://docs.docker.com/compose/how-tos/startup-order/). **Proposed/Recommended.** pm-stack check/configure/up/migrate/status/drain/backup/restore are operator commands shipped with the deployment package, not provider features in ordinary pm. The launcher validates one typed configuration with deploymentOwnership on each dependency (bundled/managed), locks only that deployment's provisioning, validates version locks, creates secrets through server-admin tooling, starts dependencies, waits on authenticated readiness and migration versions, then admits API/worker traffic. API replicas never fork databases or clusters. Managed dependency endpoints are probed but never initialized destructively, stopped, upgraded or deleted by PM stop/uninstall.

**Proposed/Recommended.** Keep database, Temporal and object service ports private; expose only TLS ingress by default. Configure authenticated interservice access and scoped service identities. Readiness includes PM schema compatibility, authorization/secret key availability and authoritative dependency health; liveness only process responsiveness. PostgreSQL unavailable means no successful new durable acceptance. Temporal unavailable may preserve already-accepted outbox intent, with bounded backlog and explicit queued/dependency-unavailable state; fail new admission once budget is reached. Storage unavailable stops publication and new transfers without advancing checkpoints. Existing UI/CLI disconnection changes no durable job state.

## Proposed budgets, recovery and acceptance

**Proposed/Recommended — targets, UNMEASURED.** Begin qualification on Linux amd64/arm64, 8vCPU/16GiB RAM/100GiB SSD minimum evaluation host, 32GiB preferred for meaningful analytical concurrency; not a production sizing guarantee. Reserve roughly2GiB PostgreSQL,2–4GiB Temporal,1–2GiB object metadata/gateways plus volume buffers,0.5GiB API,1GiB orchestration workers,4GiB per active analytical child, and OS/headroom. Child concurrency must fit physical/cgroup memory; do not add nominal budgets beyond available memory. Measure cold startup, idle footprint,100 concurrent clients,10 workspaces,20 admitted jobs and2 analytical tasks before choosing smaller host support. Separate PG/Temporal/object disk contention is likely relevant; no end-to-end throughput number is claimed.

**Proposed/Recommended.** Single-host stack is remote-accessible but not highly available. Scale worker replicas independently first; add API replicas for availability/load while retaining PG outbox arbitration and Temporal schedules. Raise object replication/master quorum and PG/Temporal infrastructure availability only with measured failure objectives and restore drills. Initial target for a small deployment: documented maintenance windows, RPO≤24h with daily coordinated backup and RTO≤4h on a preprovisioned host; these are acceptance targets, not achieved SLOs. Stricter RPO needs tested incremental/WAL/object retention procedures and operational budget.

**Proposed/Recommended.** Baseline backup quiesces new admission/schedules, drains or explicitly records unresolved activities/effects, stops Temporal and PM writers at a named cutoff, backs up PM and Temporal databases + filer metadata + referenced immutable object data + dependency configuration + encrypted key material through each owner's supported tools, and produces an integrity manifest. Never claim independent online snapshots are atomic across those systems. Restore into a quarantined stack, verify hashes/schema/key versions, reconcile PM intent/workflows/effects before provider writes resume, then require operator release. Backups cannot undo already-issued external writes; ambiguous restored effects remain unknown until reconciled. Upgrade drains/pins old workflows, expands schema compatibly, uses replay-tested worker versions, retains rollback image/data backup and never downgrades an irreversible schema in place. Uninstall preserves volumes/managed dependencies by default; purge is a separate authorized action.

**Proposed/Recommended acceptance/file obligations.** Add deploy/compose.yaml, deploy/compose.managed.yaml (provisioning override only), deploy/images.lock.json, deploy/caddy/Caddyfile, deploy/seaweed/{filer.toml.tmpl,security.toml.tmpl,s3.json.tmpl}, deploy/postgres/bootstrap.sql, deploy/temporal/{config.yaml.tmpl,dynamicconfig.yaml,schema-init.sh}, scripts/pm-stack, scripts/backup-stack.sh, scripts/restore-stack.sh, scripts/verify-release.sh and operational runbooks. Secret templates contain references/placeholders, never default credentials. Exact purpose/owner/milestone reconciled into FILE-OWNERSHIP.json by synthesis owner. Validate fresh/full/standalone/managed installation; missing secret/partial startup; two API/worker hosts with no shared filesystem; cross-workspace artifact denial; kill during upload/publication/query; corrupt object; orphan retention; outage/backlog bounds; active-workflow upgrade; restore without reissuing unknown effects; uninstall retention. These are planned application tests, not tests executed during research.
