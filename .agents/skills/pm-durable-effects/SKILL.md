# Durable effects

## Required context

Read [repository instructions](../../../AGENTS.md) and [skill routing](../../../docs/development/skills.md); use `pm-go` for Go work. Obtain the accepted task contract, state/identity ownership, affected transition examples and failure oracles. Resolve exact request/refusal/budget bindings from the owning specification. F01 refusal codes, retry disposition, count/age scopes and boundary semantics remain unresolved until explicitly accepted; synthetic 1000/1h examples are not defaults.

Name what PostgreSQL owns, what Temporal observes, what shared objects contain and what only the provider can establish. No cross-system transaction or exactly-once provider-write guarantee exists.

## Procedure

1. **Trace admission and duplicate identity.** API acceptance atomically records the immutable RunSpec, durable execution grant, scoped idempotency key/fingerprint, run/event/audit facts, budget reservation and StartRun outbox in PostgreSQL before HTTP 202. Same scoped key and same admitted fingerprint returns the original identity; changed fingerprint returns HTTP 409. Concurrent duplicates, lost responses and dependency outages must preserve that distinction. PG failure cannot accept work; Temporal failure may leave bounded pending work. Refusal details and budget equality/clock/count rules come from the accepted specification.
2. **Trace both handoff origins.** API-origin workflow ID is stable `pm/run/<opaque UUID>`; use explicit conflict FAIL and reuse REJECT_DUPLICATE policies. Reconcile AlreadyStarted against the exact binding and generation, not a guessed success. Terminal guards prevent stale outbox starts after retention; NotFound for a previously bound execution is uncertain, not permission to repeat effects. For schedule origin, the effect-free scheduled workflow first admits the nominal UTC occurrence and adopts that same execution. Do not emit a second StartRun or add PM cron. Temporal owns scheduling and orchestration; PG effect facts own business outcomes.
3. **Keep workflows deterministic and bounded.** Use Temporal workflow time, channels and concurrency primitives. Put provider/SQL/object I/O and credential resolution in activities; never use native goroutines or wall-clock/I/O inside workflow code. Bound retry policy, deadlines, payload, fanout and history. ContinueAsNew preserves PM identity, original deadline and drained control intent. Secrets and bulk data stay outside workflow history.
4. **Separate action, dispatch and attempt.** Entity identity is not an effect occurrence. Preserve effect key, exact ordered member IDs, payload hash/reference, operation revision, account witness, grant epoch, dispatch and attempt identities. Persist intent and reserve outcome/readback capacity before one physical send. Do not synthesize provider idempotency support, hide transport retries or assume fencing can unsend a request. Follow the accepted single-attempt HTTP policy; connection pooling and redirects require their own qualification.
5. **Settle exact outcomes.** Correlate each member using documented provider keys or declared order with exact cardinality. Preserve unsent, succeeded, unchanged, rejected and unknown independently. Missing, extra, ambiguous or unmapped responses remain explicit. Aggregate counts, HTTP success or a closed workflow cannot prove exact effects. Retry an ambiguous write only under a proven scoped provider idempotency/replay contract, including its retention boundary, or after independent reconciliation establishes safety. Otherwise keep unknown and require the accepted recovery path.
6. **Check grant and cancellation boundaries.** Session validity gates admission and control actions. Ordinary logout, login-session expiry, client disconnect, wait timeout or browser AbortSignal does not cancel accepted work. Durable grants have independent expiry and policy epochs. Explicit principal/grant/delegation/membership/connection/approval revocation stops new effect units at the specified boundary. Already-sent work may remain uncertain; restricted reconciliation-only read authority cannot create replacement writes. Keep cancel intent, orchestration condition and unknown-effect count separate from terminal business state.
7. **Seal worksets and approvals.** Bind approval to immutable action IDs, input/workset bytes, row cardinality, mapping/config/schema/account witnesses, expiry and budgets. Changed relevant inputs invalidate approval before new effects. Preserve the creation ledger across nonidentity profile revisions. Check exact member values and outcomes; two returned rows with wrong values are not a two-row success. Direct writes without an approved sealed plan follow the accepted planning path.
8. **Publish bytes and progress together.** Upload to unique immutable shared object keys; verify SHA-256, byte length and backend generation before PG manifest publication. ETag is not a SHA-256 substitute. Advance only the exact acknowledged contiguous prefix and manifest in one PG transaction, using complete previous checkpoint identity, revision/fence and generation witness, even for empty observations. Upload success followed by PG failure leaves an orphan, not published progress. Scratch files and host rename cannot establish cross-host durability. Preserve accepted-plan, receipt and backup references for GC.
9. **Check distributed scope.** PG admission/account permits coordinate replicas and aliases sharing a provider account; process-local concurrency limits are supplementary. Keep PM application and customer PG databases separate. Use explicit authorization plus transaction-scoped RLS; pooled connections must not retain tenant context after success, error or cancellation. A failed cleanup destroys the connection rather than lending it to another scope.

## Expected evidence

Provide the affected transition table with authoritative fields, identities, commit/send boundaries and uncertainty outcomes. Select causal failures such as PG commit loss, Temporal reply loss, concurrent duplicates, duplicate schedules, response loss, partial member results, grant revocation, stale checkpoint CAS, object success/PG failure and replay/ContinueAsNew. Record exact oracles, component/scope revisions, sanitized receipts and observed results.

Temporal SDK unit/time-skipping/replay tests establish their stated properties only. Real PG/Temporal/shared-object persistence, replicas and crash recovery require the authorized same-stack tests. Do not start services or use provider accounts merely to satisfy this skill. Partial/skipped/missing checks remain unproven.

## Boundaries

Use `pm-connector-contracts` for source/value/schema/lane fidelity and `pm-release-recovery` for backup/upgrade/restore. Do not invent admission defaults, reconstruct unknown effects as success, authorize blind replay, add a local queue or promise exactly-once provider writes.
