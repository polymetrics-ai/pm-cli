# Durable effects

## Required context

Read [repository instructions](../../../AGENTS.md), [skill routing](../../../docs/development/skills.md), and the [issue/spec tracker](../../../docs/agents/issue-tracker.md); use `pm-go` for Go work. Obtain the accepted task contract, [state and identity ownership](../../../docs/architecture/pm-server/architecture/STATE-OWNERSHIP.json), affected transition examples, and failure oracles. Resolve exact request, refusal, retry, and budget bindings from the accepted specification and canonical contracts. Synthetic `1000/1h` or test-only `3/2/30s` examples are not production defaults.

Name what PostgreSQL owns, what Temporal observes, what shared objects contain, and what only the provider can establish. No cross-system transaction or exactly-once provider-write guarantee exists.

## Procedure

1. **Trace admission and duplicate identity.** API acceptance atomically records the immutable RunSpec, durable execution grant, scoped idempotency key/fingerprint, run/event/audit facts, budget reservation, and StartRun outbox in PostgreSQL before HTTP 202. Same scoped key and same admitted fingerprint returns the original identity; changed fingerprint returns HTTP 409. Concurrent duplicates, lost responses, and dependency outages must preserve that distinction. PostgreSQL failure cannot accept work; Temporal failure may leave bounded pending work. Apply the accepted refusal precedence, finite profiles, equality boundaries, clock ownership, and count scopes exactly.
2. **Trace both handoff origins.** API-origin workflow ID is stable `pm/run/<opaque UUID>`; use explicit conflict `FAIL` and reuse `REJECT_DUPLICATE` policies. Reconcile AlreadyStarted against the exact binding and generation, not guessed success. Terminal guards prevent stale outbox starts after retention; NotFound for a previously bound execution is uncertain, not permission to repeat effects. For schedule origin, the effect-free scheduled workflow first admits the nominal UTC occurrence and adopts that same execution. Do not emit a second StartRun or add PM cron. Temporal owns scheduling and orchestration; PostgreSQL effect facts own business outcomes.
3. **Keep workflows deterministic and bounded.** Use Temporal workflow time, channels, and concurrency primitives. Put provider/SQL/object I/O and credential resolution in activities; never use native goroutines or wall-clock, filesystem, network, or SQL I/O inside workflow code. Bound retry policy, deadlines, payload, fanout, and history. ContinueAsNew preserves PM identity, original deadline, and drained control intent. Secrets and bulk data stay outside workflow history.
4. **Separate action, dispatch, and attempt.** Entity identity is not an effect occurrence. Preserve effect key, exact ordered member IDs, payload hash/reference, operation revision, account witness, grant epoch, dispatch identity, and attempt identity. Persist intent and reserve outcome/readback capacity before one physical send. Do not synthesize provider idempotency support, hide transport retries, or assume fencing can unsend a request. Follow the accepted single-attempt policy; connection pooling and redirects require their own qualification.
5. **Settle exact outcomes.** Correlate each member using documented provider keys or declared order with exact cardinality. Preserve unsent, succeeded, unchanged, rejected, and unknown independently. Missing, extra, ambiguous, or unmapped responses remain explicit. Aggregate counts, HTTP success, or a closed workflow cannot prove exact effects. Retry an ambiguous write only under a proven scoped provider idempotency/replay contract, including its retention boundary, or after independent reconciliation establishes safety. Otherwise keep unknown and require the accepted recovery path.
6. **Check grant and cancellation boundaries.** Session validity gates admission and control actions. Ordinary logout, login-session expiry, client disconnect, wait timeout, or browser AbortSignal does not cancel accepted work. Durable grants have independent expiry and policy epochs. Explicit principal, grant, delegation, membership, connection, or approval revocation stops new effect units at the specified boundary. Already-sent work may remain uncertain; restricted reconciliation-only read authority cannot create replacement writes. Keep cancel intent, orchestration condition, and unknown-effect count separate from terminal business state.
7. **Seal worksets and approvals.** Bind approval to immutable action IDs, input/workset bytes, row cardinality, mapping/config/schema/account witnesses, expiry, and budgets. Changed relevant inputs invalidate approval before new effects. Preserve the creation ledger across nonidentity profile revisions. Check exact member values and outcomes; two returned rows with wrong values are not a two-row success. Direct writes without an approved sealed plan follow the accepted planning path.
8. **Publish bytes and progress together.** Upload to unique immutable shared-object keys; verify SHA-256, byte length, and backend generation before PostgreSQL manifest publication. ETag is not a SHA-256 substitute. Advance only the exact acknowledged contiguous prefix and manifest in one PostgreSQL transaction, using complete previous checkpoint identity, revision/fence, and generation witness, even for empty observations. Upload success followed by PostgreSQL failure leaves an orphan, not published progress. Scratch files and host rename cannot establish cross-host durability. Preserve accepted-plan, receipt, and backup references for garbage collection.
9. **Check distributed scope.** PostgreSQL admission and account permits coordinate replicas and aliases sharing a provider account; process-local limits are supplementary. Keep PM application and customer PostgreSQL databases separate. Use explicit authorization plus transaction-scoped RLS; pooled connections must not retain tenant context after success, error, or cancellation. A failed cleanup destroys the connection rather than lending it to another scope.

## Expected evidence

Provide the affected transition table with authoritative fields, identities, commit/send boundaries, and uncertainty outcomes. Select causal failures such as PostgreSQL commit loss, Temporal reply loss, concurrent duplicates, duplicate schedules, response loss, partial member results, grant revocation, stale checkpoint CAS, object success/PostgreSQL failure, and replay/ContinueAsNew. Record exact oracles, component/scope revisions, sanitized receipts, and observed results.

Temporal SDK unit, time-skipping, and replay tests establish only their stated properties. Real PostgreSQL/Temporal/shared-object persistence, replicas, and crash recovery require authorized same-stack checks. Do not start services or use provider accounts merely to satisfy this skill. Partial, skipped, or missing checks remain unproven.

## Boundaries

Use `pm-connector-contracts` for source/value/schema/lane fidelity and `pm-release-recovery` for backup/upgrade/restore. Do not invent admission defaults, reconstruct unknown effects as success, authorize blind replay, add a local queue, or promise exactly-once provider writes.
